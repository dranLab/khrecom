# khrecom

A work-in-progress matching decompilation of **Kingdom Hearts Re:Chain of Memories** (PlayStation 2).

The goal is C source that, compiled with the original compiler, produces a byte-identical copy
of the game's executable. This repository contains **no game data** — you need your own dump of the disc.

## Layout

```
configure.py            splits the game with splat and writes build.ninja
requirements.txt        Python dependencies (splat, ninja_syntax, pycdlib, pyelftools)
config/<VERSION>/       one folder per game version (e.g. SLUS_XXX.XX)
  <VERSION>.yaml        splat config: segments/files and their addresses
  symbol_addrs.txt      known symbols (name = address; // type:func)
  reloc_addrs.txt       manual relocation overrides
  linker_script_extra.ld
  build.yaml            compiler + flags for this version
include/                headers (common.h; splat also generates include_asm.h, macro.inc)
include/khtypes.h       the game's basic types (INT, BOOL, FLOAT, TIMEQ, ...)
src/                    decompiled C++ code, laid out like the original (src/System/PlaySpeedCtrl.cpp + .h)
tools/
  setup_wsl.sh          one-time install of the toolchain (Ubuntu/WSL)
  extract_iso.py        pulls the boot ELF out of a disc image
  elf_info.py           sections, symbols and compiler fingerprints of an ELF
  init_version.py       creates config/<VERSION>/ via `splat create_config`
  import_symbols.py     ELF symbol table -> config/<VERSION>/elf_symbol_addrs.txt
  split_objects.py      splits code and data into the original objects (uses mdebug.py)
  gen_reference.py      C++ reference tree from the debug info (ccc's stdump/uncc)
  build_iso.py          copy of the disc image with the built ELF, for boot tests (`ninja iso`)
  objdiff.sh            runs objdiff-cli (downloaded on first use) with the generated objdiff.json
  ee_asm_compat.py      fixes up the compiler's assembly for modern binutils (used by the build)
  check.sh              the gate: configure + full build/checksum + overview (before every commit/merge)
  funcdiff.py           non-interactive per-function comparison with the original
  compare_compilers.py  one source file against every installed compiler
  candidates.py         files not decompiled yet, for handing out work
  progress.py           progress table (matched / INCLUDE_ASM / not started) for this README
  setup_worktree.sh     prepares a git worktree (links game files and tools, configures)
  download_compiler.py  fetches a PS2 compiler from decomp.me's archive
  splat_ext/            custom splat segment types (later)
iso/          (ignored) your disc image + extracted ELF
asm/          (ignored) disassembly generated by splat
build/        (ignored) build output
ref/          (ignored) reference tree from gen_reference.py
```

## Setup

Everything runs inside Linux. On Windows use WSL (Ubuntu) and **clone the repo into the WSL filesystem**
(e.g. `~/khrecom`). On a Windows drive (`/mnt/c/...`) the 32-bit PS2 compilers fail with
`installation problem, cannot exec 'cc1plus'` (they can't `stat()` files with 64-bit inode numbers),
and everything else is much slower. Splitting and the asm-only build do work from `/mnt/c`.

```sh
bash tools/setup_wsl.sh            # apt packages (mips binutils, ninja, i386 libc) + .venv
source .venv/bin/activate
```

## First steps

1. **Dump the disc** and put the image at `iso/`, e.g. `iso/khrecom.iso`.
2. **Extract the executable**
   ```sh
   python3 tools/extract_iso.py iso/khrecom.iso        # writes iso/SLxx_xxx.xx + iso/SYSTEM.CNF
   ```
3. **Inspect it**: check for leftover symbols/debug info and compiler version strings.
   ```sh
   python3 tools/elf_info.py iso/SLUS_XXX.XX
   ```
4. **Create the version config**
   ```sh
   python3 tools/init_version.py iso/SLUS_XXX.XX
   ```
   Then review `config/SLUS_XXX.XX/build.yaml` and pick the compiler matching what `elf_info.py` found.
   If the ELF still has its symbol table, import it (writes `elf_symbol_addrs.txt`):
   ```sh
   python3 tools/import_symbols.py SLUS_XXX.XX
   ```
   and if it has `.mdebug` debug info, split it into the original object files. The data split uses
   the code's references, so it needs the split `.text` assembly first:
   ```sh
   python3 tools/split_objects.py SLUS_XXX.XX --text-only && python3 configure.py
   python3 tools/split_objects.py SLUS_XXX.XX --dry-run   # check the report first
   python3 tools/split_objects.py SLUS_XXX.XX
   ```
5. **Get the compiler**
   ```sh
   python3 tools/download_compiler.py --list
   python3 tools/download_compiler.py ee-gcc2.96
   ```
6. **Split and build**
   ```sh
   python3 configure.py
   ninja                    # assembles, links, and verifies the SHA-1 of the rebuilt code image
   ```
   The first goal is for this to pass with 100% assembly. Iterate on the splat yaml
   (splitting `.text` into files, adding symbols) until it does, and keep it passing.

7. **Generate the C++ reference** (needs `.mdebug`; output is gitignored because it contains game data)
   ```sh
   python3 tools/gen_reference.py SLUS_XXX.XX
   ```
   `ref/SLUS_XXX.XX/types.h` has every type, `ref/SLUS_XXX.XX/src/` one `.cpp`/`.h` per original source
   file with class layouts, function signatures (parameter and local names) and initialized globals.
   It is a reference for writing the real code in `include/` and `src/`, not compilable as is.
   With Ghidra, export its decompilation using `tools/ccc/*/CCCDecompileAllFunctions.java` and pass
   the result with `--functions FUNCTIONS.txt` to get function bodies as well.

## Boot testing

```sh
ninja iso        # -> build/SLUS_XXX.XX/SLUS_XXX.XX.iso (the first run copies the 4+ GB image)
```

`tools/build_iso.py` writes the built ELF into the original ELF's sectors of a copy of the disc
image and updates its size in the ISO9660 and UDF directories; every other file keeps its sector.
The boot copy of the ELF gets `PhysAddr = VirtAddr` (splat's linker script sets it to the ROM
offset), and its loadable image is compared with the original's. Boot the result in PCSX2 or on
hardware. PCSX2 identifies games by serial *and* ELF CRC: settings and patches keyed by the CRC of
the original ELF won't apply to the rebuilt one.

## Decompiling a file

1. Create `src/<path>.cpp` (or `.c`, see the source path in the yaml comment): its existence switches the
   file's code to the compiled object; `configure.py` writes the effective config to `build/<VERSION>/`, and
   `config/<VERSION>/<VERSION>.yaml` is never edited by hand. The file's data comes from the compiled object
   once the source lists the sections in a comment, best as its last line (no line numbers shift):
   ```cpp
   // SOURCE DATA: .data .rodata
   ```
   Until then the data stays the original assembly (see `object_fixups` and `source_config` in `configure.py`).
2. Write `src/<path>.cpp` and `.h`, starting from `ref/<VERSION>/src/<path>.cpp` (names, signatures,
   class layouts). Functions not done yet stay as
   `INCLUDE_ASM("asm/<VERSION>/nonmatchings/<path>", <name>);`, in the original order.
   Things to know about how the original was built:
   - Inline functions defined in a class are emitted (weak) at the end of the file that defines the
     class's first non-inline virtual function; a class whose virtuals are all inline or pure gets
     no vtable of its own. Weak functions at the end of an object are such inlines.
   - Headers are included as `"System/..."` (paths relative to `src/`): `__FILE__` then reads
     `src/System/...`, which the build turns into the original `c:/KHCOM/MainApp/System/...`.
   - `python3 tools/compare_compilers.py SLUS_XXX.XX src/<path>.cpp` compiles a file with every installed
     compiler and compares each function with the original.
3. Re-run `configure.py`, then compare with objdiff and iterate:
   ```sh
   tools/objdiff.sh diff -u System/PlaySpeedCtrl     # interactive, rebuilds when you save
   ninja                                            # the whole image must still match
   ```
   objdiff compares against `build/<VERSION>/expected/units/<path>.o`, assembled from the original for
   every unit (`ninja expected`). Each unit also has decomp.me scratch settings in `objdiff.json`.
   `python3 tools/funcdiff.py <path> [<function>]` is the non-interactive version (used by agents).
4. `tools/check.sh` before committing: configure, full build with checksum, and an overview of the files
   compiled from source (`INCLUDE_ASM`'d functions are counted separately).

## Parallel decompilation with Claude Code

One Claude Code session coordinates; sub-agents decompile one file each in their own git worktree.

- `CLAUDE.md`: project knowledge every session and sub-agent loads (toolchain, conventions, pitfalls).
- `.claude/agents/decomp-worker.md`: the worker's procedure - prepare the worktree, write the source,
  match it with `funcdiff.py`, pass `tools/check.sh`, commit on `decomp/<file>`, report.
- `.claude/commands/decomp-batch.md`: `/decomp-batch [n] [hints]` for the coordinator - pick files with
  `tools/candidates.py`, start `n` workers with worktree isolation, merge their branches one by one
  (`--no-commit`, `tools/check.sh`, then commit or abort), clean up worktrees.
- `.claude/settings.json`: permissions for the build/test commands, so workers don't stall on prompts.
- `tools/setup_worktree.sh` links `iso/`, the compilers, wibo, ccc, objdiff, `ref/` and `.venv` from the main
  checkout into a worktree and configures it; `tools/candidates.py` lists open files (size, functions,
  header strings in `.rodata` - files sharing headers shouldn't run in parallel).

Run the coordinator inside WSL, in the main checkout, on `main`:
```sh
cd ~/khrecom && claude
> /decomp-batch 3
```
Workers edit files, so start it with `--permission-mode acceptEdits` (or approve edits as they come).
Each worker runs `configure.py` and full builds (~200 MB disk per worktree, CPU while building).

## Notes

- **Status:** `ninja` rebuilds a byte-identical code image of SLUS_217.99 (see [Progress](#progress) for how
  much of it is compiled from C/C++). The ELF still has its symbol table (18k symbols) and `.mdebug` debug info;
  the game is C++ built with EE-GCC 2.9x (`gcc2_compiled.` markers, GCC 2 name mangling).
  Code and data are split into the original objects (game code under `System/`, `Game/`, `Form/`,
  Sony SDK / newlib / libgcc under `lib/`): 665 `.text`, 232 `.data`, 373 `.rodata` and 105 `.bss`
  units. Objects without debug info are `lib/nodebug/<first symbol>` (their data boundaries are
  approximate), uninitialized globals the linker placed last are `common`; `.sndata`, `.sdata` and
  `.sbss` are single files.
- `mips-linux-gnu-as` aligns every section to 16 bytes, the original toolchain didn't, and Sony's
  linker script starts each section at `ALIGN(128)`. `configure.py` resets each object's sections to
  the alignment its original address implies (see `object_fixups`).

- **Toolchain:** SN Systems ProDG, all Windows executables run under [wibo](https://github.com/decompals/wibo):
  compiler `ee-gcc2.95.3-136` with `-O2 -G0 -fno-exceptions -fno-rtti -g`, assembler **Ps2EeAs** (from the
  same package). Only this combination matches every function of `ColorFader`; 2.95.3-114, 2.95.2-273a
  (each with its own Ps2EeAs), the Linux 2.9 builds and Sony's 2.96 don't.
  - Ps2EeAs inserts the EE's hazard nops and pads divisions and short loops (hardware errata). Its
    divisions rule fires near labels, and `-g`'s line-number labels decide where: without `-g` the
    padding differs. `-g` changes no instruction otherwise.
  - The anonymous namespace names in the ELF (`...cppM1aaaa`, from a `c:\` path) have the low-entropy
    suffix only the Windows compilers produce; only `build.cpp` has exception tables; vtables have no
    RTTI slot.
- `tools/ee_asm_compat.py` sits between compiler and assembler: it gives anonymous namespaces their
  original names (`_GLOBAL_$N$c__KHCOM_...cppM1aaaa`) and source paths in strings their original
  `c:/KHCOM/MainApp/` prefix. Ps2EeAs can't read splat's macros, so `INCLUDE_ASM` files are inlined with
  the macros expanded and every instruction that needs no relocation written as a `.word`: otherwise
  Ps2EeAs would add its erratum padding a second time. (Without Ps2EeAs, it targets modern gas instead.)
  Ps2EeAs crashes under wibo instead of printing an error, so a crash in the `cc` step means an
  assembler error; `ee_asm_compat`'s output is in `build/.../<file>.o.s`.
- **`.rodata` layout of an object:** first the string literals of the inline functions of every included
  header, in include order and whether used or not (assert/allocation messages such as
  `"c:/KHCOM/MainApp/System/Graphic/Gprim.h(613)"`, `"m_V"`); then the constants of the file's own
  functions; vtables last. Nothing references the unused header strings, so `split_objects.py` assigns
  unreferenced data before a file's first referenced item to that file (they used to land with the
  previous file). To match a file's `.rodata`, its headers must reproduce those strings, `__LINE__`
  included.
- objdiff can report less than 100% for data that matches: the target objects contain splat's
  `.word func_0` relocations for zero words (e.g. empty vtable slots) and the padding before the next
  object, the compiled ones don't. The full build's checksum is what counts.
